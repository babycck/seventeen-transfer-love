## 用户需求

审查并修复 Transfer 模式「事件池」中存在的不合理与死数据问题，使其与触发逻辑一致、事件可正常触发。

## 产品概述

当前事件池（秘密任务池、随机日常事件池）存在数据定义与触发逻辑自相矛盾的情况，导致大量事件永不触发或标注错误。本次修改在不改变整体架构与 AI 调用链路的前提下，修正死数据、死条件与标注错误，让已定义内容真正生效。

## 核心功能

- **秘密任务放行 Day 2 + Day 7**：删除约会日 Day 5/10 的死数据（符合"自由约会"设计），并将 Day 7 从触发排除列表移除，使 Day 7 上午可正常触发秘密任务。
- **修复随机事件 re_10 死事件**：将无效条件 `affection>=30`（恒为假）改为 `day>=4` 天数门控，使"撞见旧伤"可触发。
- **修正随机事件池标注与 id 跳号**：修正"15个/6个"的错误注释为实际数量，并将 re_15→re_14、re_16→re_15 重编号消除缺口。
- **补全「空调坏了」季节覆盖**：为春/秋补充 re_2_spring / re_2_autumn，使该事件全年可触发。

## Tech Stack

- 语言/运行时：JavaScript (ES Modules)，Node.js 18+
- 框架：Vanilla JS + Vite
- 不引入新依赖，所有改动使用浏览器原生 API

## Implementation Approach

### 核心策略

仅做数据层与触发排除列表的精准修正，不改动 `evaluateCond` 的 `affection` 语义（涉及其余事件的解析器，改动面大、风险高），转而把无法用现行 cond 表达的"成员好感"语义降级为天数门控。秘密任务的修复采用"删死数据 + 放行 Day 7"两步走，与用户已确认决策一致。

### 关键技术决策

- **秘密任务**：`SECRET_MISSIONS` 仅保留 Day 2 / Day 7 两块数据，删除 Day 5 / Day 10（约会日不放秘密任务）。`utils.js` 的 `shouldTriggerSecretMission()` 中 `mandatoryDays = [1,3,6,7,11,12]` 移除 7（Day 7 仅傍晚 questionBox 占用，上午空闲），使 Day 7 秘密任务可触发。
- **re_10 条件**：`cond: 'affection>=30'` 因 `resolveValue('affection')` 取的是 `affections['heroine']`（恒为 0）而永假，改为 `cond: 'day>=4'`，使其在进入中段剧情后自然出现。
- **id 重编号**：`re_15`→`re_14`、`re_16`→`re_15`（已核实无外部引用，仅 data.js 与备份出现），消除 re_13 直接跳 re_15 的缺口。
- **re_2 补全**：新增 `re_2_spring`（"空调时好时坏"）、`re_2_autumn`（"秋燥静电/空调调试"）两个季节分支，与既有 summer/winter 并列，覆盖全年。

### Performance & Reliability

- 纯数据/条件修正，无新增 AI 调用，零运行时开销。
- 不改动 `evaluateCond` 解析器，避免影响其它事件（re_8 的 `weather==晴朗`、re_13 的 `drinkCount>=1` 等仍正常工作）。
- 删除的 `SECRET_MISSIONS[5]/[10]` 仅定义数据，无运行期引用，删除安全；`secretMission` 运行态在跨天 `cleanupSecretMission()` 已正确清理，不受影响。

## Implementation Notes

- 遵循现有代码风格：`var` 声明、`+` 字符串拼接、不使用模板字符串。
- 不引入新依赖，不改动 1v1 模式逻辑（本次修改均位于 Transfer 数据/触发路径）。
- 修改 `SECRET_MISSIONS` 后需确认 `shouldTriggerSecretMission()` 的 `SECRET_MISSIONS[GS.day]` 读取在 Day 5/10 返回 `undefined`（自然 return false），无需额外兜底。
- 重编号 re_14/re_15 仅改 id 字符串，desc/name/weight 不变；务必确认 `app.js.backup` 仅为旧备份、不参与构建。
- 修改后本地 `npm run dev` 跑一局 Transfer 模式，验证 Day 2 / Day 7 上午能弹出秘密任务、随机事件池无报错。

## Architecture Design

本次为数据层与触发守卫的小幅修正，复用现有 `SECRET_MISSIONS` 读取链路（`shouldTriggerSecretMission` → `SECRET_MISSIONS[GS.day]`）与 `RANDOM_EVENTS_POOL` 概率抽取链路（`shouldTriggerRandomEvent` → `evaluateCond` 过滤 → 加权抽取），不改变模块边界与调用顺序。
