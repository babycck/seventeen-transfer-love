## 产品概述

ENTSIM（`src/ent-sim/`）是《换乘恋爱 × SEVENTEEN》中「娱乐圈模拟器」子系统，玩家在练习生或女团爱豆身份下与一名 SEVENTEEN 成员展开慢热恋爱。本次任务要求对其进行全量代码审计，重点聚焦池子质量、AI 上下文记忆、游戏逻辑自洽性，并输出可落地的优化建议与不少于 50 个游戏理解问题。

## 核心审计目标

1. 池子系统审计：检查 `pools/` 下 140+ 池子的导出完整性、重复/占位/未使用、权重与主题分布。
2. AI 上下文记忆审计：梳理 prompts.js / memory.js 实际注入字段，定位 AI 会「失忆」的本地状态。
3. 游戏逻辑审计：好感度、曝光、情敌、哥哥、告白、掩护、公关、练习生阶段、章节推进等数值与状态机。
4. 代码质量审计：空引用、字段不一致、死代码、硬编码魔数、异步锁、函数过长等 bug 与坏味道。
5. 优化建议：池子增删、游戏体验、数值平衡、记忆增强、UI 反馈、结局分支等方向。
6. 提出不少于 50 个游戏理解问题，供后续设计与调优讨论。

## 关键问题预览（已确认）

- P0：`romance.js` 84 好感度阶段死锁，`stageMax` 与 `checkRomanceUnlock` 阈值冲突导致无法升到 85。
- P1：情敌名 fallback 到男主名、`GS.oneHeartRomanceStage` 在 entSim 中未维护导致 validator 失效、UI 与 engine 字段不一致。

## 核心问题详解

### P0：好感度 84 死锁（`romance.js`）

- `checkRomanceUnlock` 返回 stage 4 需要 `aff >= 85` 或 `oneHeartRomanceStage >= 3`。
- `applyEntSimAffection` 中 `stageMax` 数组为 `[19, 49, 69, 84, 100]`，对应 `unlock.stage`。
- 当 `aff = 84` 时，`unlock.stage = 3`，`stageMax = 84`，任何正 delta 被截为 0。
- 结果：玩家无法通过正常 affectionDelta 从 84 升到 85，除非告白成功 +10 或直接改写 `E.affection`。
- 修复建议：统一阈值，令 `stageMax` 比下一阶段触发阈值大 1，例如 `[20, 50, 70, 85, 100]`，或调整 `checkRomanceUnlock` 的 stage 4 条件为 `aff >= 84`。

### P1：情敌名 fallback 到男主名（`brother.js` / `state.js`）

- `state.js` 初始化 `npc_suitor` 但从未初始化 `E.rival`。
- `brother.js:234` 使用 `(E.rival && E.rival.name) || (E.romance && E.romance.maleLead && E.romance.maleLead.name)`。
- 当 `E.rival` 不存在时，情敌名 fallback 为男主名，导致「男主在追求女主」的叙事错误。
- 修复建议：统一使用 `E.npcNetwork.nodes.npc_suitor.name` 或 `GS.oneHeartRival.name`，移除 fallback 到男主名的逻辑。

### P1：validator 基于错误阶段字段（`validator.js`）

- `validator.js:40` 读取 `GS.oneHeartRomanceStage`，但 entSim 模式几乎不维护该字段。
- 导致禁忌词、越级选项、affectionDelta 上限检测全部基于 stale 值。
- 修复建议：validator 应读取 `GS.entSim.affection` 并通过 `affectionStageIndex` 计算当前阶段。

### P1：UI 与 engine 字段不一致

- `ui.js:513-531` 约定面板读取 `E._aptCards`，但 `engine.js:324-341` 写入 `E.appointments`。
- `ui.js:1634` 联系人读取 `E.maleLead.name`，实际状态在 `E.romance.maleLead`。
- `ui.js:1089-1094` 探班读取 `E.romance.rival`，该字段未初始化。
- `ui.js:1843` `__phoneSend` 在 brother/rival 分支使用未声明变量 `replyContent`。
- 修复建议：统一字段名，补全 null 检查，修复未声明变量。

### P1：曝光 / PR 状态不同步（`public-opinion.js` / `engine.js` / `ui.js`）

- `E.misc.prRemaining` 初始为 2，但代码中没有真正消耗它的公关逻辑。
- `ui.js:642` 显示公关次数为 `Math.min(5, 1 + Math.floor(pop/30))`，与状态不同步。
- `addExposure` 无上限，曝光容易单向膨胀。
- 修复建议：将公关逻辑与 `prRemaining` 绑定，统一 UI 显示来源，给 `scandalHeat` 加软上限或更积极衰减。

### P2：AI 失忆字段清单

以下本地状态已结算但未被注入 prompt，导致 AI 无法感知：

| 状态 | 影响 |
| --- | --- |
| `E._affDayTotal` | AI 不知道每日好感上限，可能继续写高 delta |
| `E._jealousLevel` 精确值 | 叙事强度可能与系统状态不一致 |
| `E._romanceMilestones` | 无法主动引用纪念日 |
| `E.appointments` | 忘记约会约定 |
| `GS._entSimChatHistory` / 每日计数 | 主剧情不知道今天聊了多少条 |
| `E.romance.coverUsed` | 重复写掩护桥段 |
| `E.diarySummary` | 生成后无读取入口 |
| `E.fanReactions` / 泡泡反馈 | 营业后的粉丝反应不进入主剧情 |
| `E._entSimPendingOffers` | 暂存的代言/综艺邀约被遗忘 |
| `E.brother.testNudged` / `talkPending` | 考验触发记录与谈话 pending 不注入 |
| `E.flags` 门控 | AI 无法感知关键分支锁 |


### P2：memory.js 压缩机制缺陷

- 压缩源是 `_entSimNarrativeBuffer`，只含 `parsed.narrative`，不含分支标签和玩家选择。
- `careerHistory` 包含大量日常人气变动，容易稀释关键事件。
- 压缩失败兜底取前 80 字，若开篇是环境描写则关键事件丢失。
- 没有按事件重要性加权，也没有区分「已解决 / 未解决」悬念。
- 改进建议：压缩时加入玩家选择文本；给关键事件类型打权重；保留未解决悬念列表。

### P2：日程系统冲突与污染（`cycle.js`）

- 四人行程独立抽取，无去重/冲突检测，可能出现男主与情敌同时在同一地点做同一件事。
- `_used*` 数组是模块级全局，存档重载后仍保留上一局记录，污染新游戏日程池。
- 改进建议：增加行程冲突检测与去重；将 `_used*` 数组移入 `GS.entSim` 存档。

### P2：哥哥支持度状态机矛盾（`brother.js` / `engine.js`）

- `maybeBrotherEvent` 声明只注入剧情不改支持度。
- `checkOneHeartEvents` 却可直接 `E.brother.support += ev.support`。
- `engine.js:applyBrotherEffect` 要求 `GS._entSimCurrent.type === 'choice'` 才允许改支持度。
- `talkPending` 置位后无任何读取/清除逻辑，是死状态。
- 改进建议：统一支持度变更入口，补全 `talkPending` 的 UI/prompt 消费。

## 优化建议

### 池子优化

1. 补齐 `pools/index.js` 导出：决定 `company-events.js` 与 `chat-ack/` 是接入还是删除，避免「看起来存在但不可用」。
2. 合并主题重复的池子：如 `jealousy-events.js` 与 `romance-jealousy.js`、`dating-rumors.js` 与 `dating-scandal-chain.js`，减少 AI 抽取时的主题冲突。
3. 为高频场景增加权重或分层：练习生期多训练/月评，出道后多打歌/签售/综艺，避免后期抽到前期池子文本。
4. 增加「空白期」专用池：出道后无回归时填充焦虑/兼职/练习室日常，避免剧情空转。
5. 情敌攻势池按「亲密度」而非女主好感度驱动，与系统设计文档对齐。
6. 为每个池子增加 `weight` 或 `frequency` 元数据，避免所有事件等概率触发导致高频低影响事件稀释主线。

### AI 记忆优化

1. 构建「关键状态注入清单」，将 `appointments`、`coverUsed`、`jealousLevel`、`romanceMilestones`、`flags` 等加入 prompt。
2. 在 `buildEntSimContextSnapshot` 中增加「未解决悬念」段落，列出待赴约、待公关、待处理事件。
3. 压缩 memory 时保留玩家选择文本，使用 `{choice, consequence, keywords, events}` 结构。
4. 给 `careerHistory` 增加重要性评分，过滤日常人气波动，只保留关键节点。
5. 跨天保留昨日结尾 600 字 + 最近 3 天摘要 + 未解决悬念，避免跨天记忆过薄。

### 数值与游戏逻辑优化

1. 统一 `AFFECTION_STAGES`、`ROMANCE_DEPTH_LABELS`、`stageMax`、`checkRomanceUnlock` 阈值，消除死锁。
2. 给 `scandalHeat` 加软上限（如 40）并引入事件驱动衰减（公关成功、低调一周）。
3. 将 `prRemaining` 与 UI 显示统一，明确手动公关消耗与恢复规则。
4. 练习生阶段与出道后的数值曲线应明显不同：练习生人气低但曝光伤害小，爱豆人气高但曝光伤害大。
5. 章节跃进改为剧情化时间跳跃（生成一段过渡文本），而非直接修改 `dayCount`。
